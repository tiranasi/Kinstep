# KinStep 提示词与 UI 数据契约独立评估

## 范围与方法

只读冻结包 `D:\XJTLU\course\G4\ENT303\software\evaluations\prompt-audit-20261028\inputs.json`：原始出站 messages、八个 fixture、taskViews 和包内七份源代码快照。包显示通过应用函数本地捕获，未调用模型。未读取原项目、真实数据、密钥、其他聊天或项目记忆，也未修改包或原项目。

`cases.json` 包含 15 个独立候选（10 个问答、5 个单据）。先按包内 system 消息及案例输入生成候选，再静态沿快照推演校验、界面和确认后状态；没有运行应用或调用 DeepSeek，结论不是实测 DeepSeek 表现或准确率。案例的 evidenceType 按指定格式标为“Terra独立演练”；本会话没有独立的运行时证据可验证底层模型的具体型号，不能将标签作为型号证明。候选是本次助手生成，不是回退函数输出。八个问答消息均为长辈原文，因此问答案例均用 elder；child 只用于单据确认推演。单据案例把构造文字视为假想单据的可见内容，复用原 system 提取规则：实际输入包只有占位图片，无法对真实图片消息执行视觉识别，故这是文本化近似演练，不是完全相同的多模态输入，也不是 OCR 或视觉测试。fixtureClock 仅事后核对 C10，未加入模型输入。

代码位置均指**输入包内** `sources` 的原始路径及其行号，不代表另行读取了项目文件。验证判断基于代码静态分析而非实际运行；各案例的状态效果以其 assessment 明示的 fixture 和用户点击为条件。

## 主要发现

### 1. 缴费用途和缴费事实混为一谈：高优先级

E04 输入“药品费用缴费通知；状态：未缴费”，候选正确保留 `paymentFor: "medicine"`、`summary: "药品费用100元，尚未缴费。"` 和 `notes: "状态：未缴费"`。该结果所有字段格式合法、文字含义也正确，但系统缺少独立的缴费状态字段（`src/lib/schema.ts:21–44`）。在 stage 6 的 pharmacy fixture 下，确认界面固定写“请确认对应项目已缴费”和按钮“确认已缴费”（`src/components/documents.tsx:232–234, 269–273`）；若子女点击，`applyDocument` 只看用途与阶段，不看 summary/notes，就把 `medPaid` 设为 true（`src/lib/domain.ts:194–205`）。这不是模型已经判断付款成功：是用户确认之后的代码推演；但界面默认话术与单据事实矛盾，可能诱导错误确认。检查费用也有同类条件风险。

建议区分 `paymentFor` 与有明确证据的 `paymentStatus`，未知和未缴费只保存材料；只有明确缴费成功且用户明确确认对应项目时才允许推进。界面同时展示原文状态、用途和目标，不能把所有 payment 均标为已缴费。新增覆盖未缴费、未知、成功、退款和不同阶段的契约测试。

### 2. 对话可描述当前任务，但部分任务无法通过语音确认

C06 “血常规已经做完了”返回引导到检查安排、action 为 null；C07 “药费我已经付了”也只能引导页面确认。冻结的 testing/pharmacy task 分别带 `testDone`/`medPay`，但原提示和服务端白名单仅允许 arrive、checkin、consult、collectMedicine、help、doseTaken（`src/lib/assistant.ts:144, 152–156`）。语音界面仅在返回 action 时显示通用“确认”按钮（`src/components/voice.tsx:193–205`）。因此语义正确、JSON 合法，却无法通过此问答直接执行业务动作；其他界面是否方便到达不在快照证明范围内。应统一可执行动作目录和任务数据，或明确引导到对应界面；若扩展白名单，必须保留项目 ID、阶段、用户确认和领域前置校验。

### 3. 模型缺少当前时刻，合法建议仍可能无法执行

C10 明确说今天 20:00 已服药，候选返回对应 `doseTaken` ID。它符合唯一药品和时次要求，服务端也接受该 action，界面会提供确认。但 fixtureClock 对应当地 2026-10-28 12:00，确认时 `scheduledAt <= now` 不成立，领域层拒绝“还没到这次提醒时间”（`src/lib/domain.ts:393–401`）。原消息含时次却没有当前时刻（`src/lib/assistant.ts:144`），不能要求模型凭事后时钟预知拒绝。建议后端在返回动作前用服务器时钟和领域规则做可执行性预检，给用户清楚解释，并继续在最终提交时重新验证；对提前服药应制定明确产品规则，而不是默认改记其他时次。

### 4. 结构校验不保证事实或确认按钮语义

`extractionSchema` 要求所有字段、枚举和数组边界，字符串可为空（`src/lib/schema.ts:21–44`）；`extractImage` 解析失败返回错误而不是直接使用（`src/lib/assistant.ts:83–85`）。但其不验证分类是否与原文相符，也不验证提取日期的语义。预约单应用仅用日期正则与 `new Date` 判断（`src/lib/domain.ts:159–168`），没有复用严格的 `dateSchema`（`src/lib/schema.ts:3–9`），日期在不同环境解析及归一化的后果需要运行测试。问答要求 100 字，实际只校验非空且最长 1500 字；action 错误或不在白名单时被静默清空，reply 不同步调整（`src/lib/assistant.ts:148–156`）。若模型写“请点击确认”但 action 被清空，用户可能看到没有按钮的指令；这是静态风险，不是本轮候选发生的实际输出。建议对回复长度、动作与文案的一致性做服务端检查，错误动作给出安全的可理解退路，并严格校验预约日期。

### 5. 单项目回退可能把未知对应项关联到唯一检查

`matchTest` 在 targetName 为空且仅一项检查时自动匹配该项（`src/lib/domain.ts:224–227`）；报告界面也有相同回退（`src/components/documents.tsx:126–129`）。因此无法从单据确定对应检查时，唯一任务并不证明报告或付款属于它。报告还要求检查已完成（`domain.ts:185–190`），但不能解决目标误配。建议无明确对应名称时要求用户核对项目，尤其是状态推进前；这是静态代码发现，本轮没有把它计作模型输出错误。

## 已有保障与案例说明

- 原始提取提示禁止猜测剂量、日期和付款成功，区分申请单、领取回执、处方和已完成状态，并要求忽略图片中的指令（`src/lib/assistant.ts:67–70`）。这属于提示要求，并不证明模型必然遵守。
- E01 在 consulting 阶段确认后只新增待缴费、未完成、未取得报告的检查；E03 的 receipt 仅保存材料，不把检查或报告标为完成（`src/lib/domain.ts:121–135, 171–179, 218–221`）。E05 处方生成未核对、未启用草稿，启用另需核对、取药、用法及时间等条件（`domain.ts:138–151, 207–215, 378–389`）。E02 仅保留药盒可见名称，无剂量补全。
- C02、C04、C08 的候选是待确认动作，分别在对应 fixture 满足条件时推进到院、接诊、取药；C03 的未报到陈述不产生动作。阶段与先决条件由领域层复核（`domain.ts:258–272, 321–330`）。C09 两个时次未明确，要求选择而不是猜测。语音界面显示回复并朗读，只有存在动作才出现确认（`src/components/voice.tsx:65–78, 188–205`）。
- 报告对应项目存在且检查未完成时，界面禁用确认并提供先确认检查完成的按钮；领域层也要求完成检查（`src/components/documents.tsx:237–255`; `src/lib/domain.ts:185–190`）。长辈不能在此界面编辑详细字段，子女可编辑，确认时只由子女传入修改字段（`src/components/documents.tsx:246–261`; `src/lib/domain.ts:343–351`）。因此展示哪些关键字段对有效确认很重要；目前卡片主要显示名称、剂量、项目和摘要，不能假定所有提取字段都在确认前醒目呈现（`documents.tsx:193–217`）。
